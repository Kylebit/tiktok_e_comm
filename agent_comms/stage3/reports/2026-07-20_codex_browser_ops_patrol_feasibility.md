# Codex 内置浏览器做店铺日常运营巡检可行性评估

任务：#0036  
执行方：Orbit Codex  
日期：2026-07-20

## 可行性结论

可以做，但不建议把“直接操作平台后台网页”作为店铺运营自动化的主链路。更稳妥的方案是：API 优先，浏览器补盲，关键动作人工确认。

内置浏览器适合做低频、只读、风险可控的巡检，例如查看是否有新的客服消息、广告余额是否低于阈值、订单列表里是否有快超时订单，并把截图/页面摘要/链接发给 Boss 或运营人员。它不适合作为高频无人值守的核心生产链路，也不适合自动点击会影响账户、资金、广告投放或客服承诺的按钮。

推荐落地级别：

- P0：只读巡检和提醒，可以做。
- P1：半自动辅助处理，可以做，但需要人工确认。
- P2：自动回复、自动调预算、自动取消/发货/退款，不建议先做，除非平台 API、权限和审计链路完备。

## 能做什么

### 客服消息巡检

可行。Codex 内置浏览器可以打开店铺后台，读取页面是否有未读消息、超时提醒、会话数量、明显的红点/徽标，并把结果汇报给总控。

更建议只做提醒，不直接代替客服回复。TikTok Shop 自身已经提供 Chatbot、Recommended Answers、Saved Replies 等自动化能力，说明客服自动化更适合在平台认可的工具体系内做，浏览器巡检可以作为提醒层。

### 广告余额巡检

可行。可以打开广告后台，读取余额、消耗、暂停/余额不足提示。风险比客服回复低，因为它可以做成只读。

不建议让浏览器机器人自动充值、自动大幅调预算、自动启停广告。资金类和投放类操作需要人工确认和操作日志。

### 快超时订单巡检

可行。可以按页面筛选待发货/待处理/异常订单，读取倒计时、承诺发货时间、物流异常提示，生成“需要处理”的清单。

如果平台提供订单 API，应优先用 API。浏览器方案适合作为没有 API、API 字段不全、或临时验证后台状态时的补充。

## 卡点与风险

### 1. 登录态和 MFA

浏览器自动化最大的实际卡点是登录态。平台可能要求短信、邮箱、Authenticator、扫码、人脸、设备验证或风控验证。TikTok Shop 近年来也在加强身份验证和账户安全，自动化后台登录容易遇到额外验证。

建议：使用一个固定、低权限、只读或运营巡检账号；浏览器只复用已登录会话，不在无人值守流程里处理 MFA。

### 2. 验证码和反自动化

电商平台通常会保护登录、消息、订单、广告等高价值入口，验证码、设备指纹、行为检测和频率限制都可能触发。业内也在讨论浏览器代理、机器人认证、反机器人识别等问题，这说明“浏览器像人一样点网页”并不等于长期稳定。

建议：低频访问、固定环境、不要多账号并发、不要伪装规避风控；遇到验证码就停止并提醒人工。

### 3. 页面结构变化

后台页面经常改版。浏览器脚本依赖按钮文案、CSS 选择器、表格位置、路由结构，稳定性低于官方 API。尤其是多语言后台、A/B 测试、弹窗、活动横幅、公告遮罩，都会导致误判。

建议：以“页面文本 + 视觉校验 + 宽松选择器”为主，不依赖单个 fragile selector；每次巡检保存摘要、时间、截图和异常原因。

### 4. 权限和账号安全

如果让自动化浏览器拥有完整后台权限，一旦提示注入、页面误点、会话泄露或机器被接管，影响会很大。广告预算、客服回复、退款、订单履约都属于高风险动作。

建议：最小权限账号，禁用资金和敏感操作权限；所有写操作必须二次确认；日志中不要保存 cookie、token、完整个人信息。

### 5. 频率限制和平台条款

浏览器方案可能被平台视作异常自动化访问。即使没有明确禁止，频繁刷新后台、批量打开订单或模拟人工操作，也可能触发风控。官方 API/合作伙伴能力通常更可维护、更合规。

建议：把浏览器巡检频率控制在接近人工查看的水平，例如 10-30 分钟一次消息/订单摘要，广告余额 1-2 小时一次；失败退避，不连续重试。

## 与官方 API 的对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 官方 API | 稳定、结构化、可审计、适合高频和生产链路 | 接入成本高、权限申请慢、部分后台信息不开放 | 订单、库存、广告数据、客服工单、财务报表 |
| 内置浏览器 | 上手快、能覆盖 API 没有的页面状态、适合临时补盲 | 登录/验证码/风控/页面变化风险高，难长期无人值守 | 只读巡检、截图核验、异常提醒、临时运营看板 |
| 混合方案 | 兼顾稳定和覆盖面 | 需要设计降级和审计 | 推荐主方案 |

## 推荐方案

### 推荐架构

1. API 层优先拉取结构化数据：
   - 订单超时、履约状态、客服 SLA、广告消耗、余额、结算数据。

2. 浏览器巡检层只做补盲：
   - 登录后台看红点、公告、余额提示、风控提示、异常弹窗。
   - 读取页面摘要，保存截图。
   - 不直接执行资金、客服、履约动作。

3. 人工确认层：
   - 对“要回复客户”“要调整预算”“要处理订单”等动作，生成待办卡片。
   - Boss 或运营确认后再执行。

4. 审计与降级：
   - 每次巡检记录平台、账号、页面、时间、结果、截图路径、失败原因。
   - 遇到登录失效、验证码、页面结构异常，立即 BLOCKED/提醒，不重试轰炸。

### 最小可行试点

第一阶段建议只做 3 个只读巡检：

1. 客服消息红点巡检：
   - 输出：未读数量、最早未处理时间、页面截图。
   - 动作：提醒 Boss/运营，不自动回复。

2. 广告余额巡检：
   - 输出：余额、消耗、低余额阈值状态。
   - 动作：低于阈值提醒，不自动充值。

3. 待处理订单巡检：
   - 输出：快超时订单数量、订单号、剩余时间、后台链接。
   - 动作：生成待办，不自动取消/发货/退款。

### 是否建议做

建议做“只读巡检 + 人工确认”的版本。  
不建议做“全自动后台操作”的版本。

这类能力对 Orbit 有价值：它能覆盖平台 API 没开放或临时变更的后台信号，也能作为运营 morning check / evening check 的自动提醒。但它必须被设计成“保守的观察者”，而不是“无人值守的后台操作者”。
