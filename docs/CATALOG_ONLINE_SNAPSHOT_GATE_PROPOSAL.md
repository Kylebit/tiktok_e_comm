# Catalog online snapshot: technical evidence proposal

Status: **proposal / policy HOLD**. `shared_platform/catalog_online_snapshot_gate.py` is not called by the web service, deployment helper, or formal JIT runner. Its receipt always says `TECHNICAL_VERIFIED_POLICY_HOLD` and `execution_authority=false`. A successful synthetic test is not permission to back up a formal database or switch a Task.

## Why the existing gate stays closed

The current f3 JIT contract requires three quiet physical samples and holds on an unexplained nonempty SQLite sidecar. The observed 32 KiB `catalog.db-shm` with a zero-length WAL is therefore a **HOLD**, even if the main database SHA is stable. `mxFrame=0` and WAL length zero show no uncheckpointed WAL frames at those instants; they do not prove that no reader has the database open. A raw copy of the main `.db` is not a consistent online backup. `docs/DATABASE_GOVERNANCE.md` permits the SQLite online backup API as a backup method, but does not waive the f3 sidecar/JIT rule.

## Proposed alternate technical evidence

Only after a separate work order authorizes the exact source and private destination, the gate can attempt the following bounded operation. Any missing, changing, oversized, malformed, or contradictory fact is a HOLD. A failed attempt may leave a partial private backup; it never leaves a passing receipt.

1. Resolve and bind the expected source path. Reject symlink source/sidecars, source/output overlap, and **any existing private destination directory**, including one containing a backup, receipt, or SQLite sidecar. The caller supplies fresh expected main and SHM SHA-256 values from a separately sealed source-identity sample. The gate atomically creates the destination directory only after source preflight; a pre-existing backup journal/WAL/SHM cannot be a destination sidecar. This does not exclude another process from racing into the new directory: a reviewed private ACL and single-writer operating contract are required for any formal use, and neither is verified by this module.
2. Sample main, WAL, SHM, and journal existence, file IDs, sizes, modification times, and SHA-256. Require a WAL-mode main header, zero-length WAL, exactly 32 KiB SHM, byte-identical 48-byte WAL-index header copies, the native-endian checksum over bytes 0–39, version/padding/initialization/flag checks, `mxFrame=0`, and consistent page/backfill fields. Repeat after a quiet interval. An empty newly initialized WAL-index may have `szPage=nPage=0`; this is recorded as **unbound**, while a nonzero page size must match the main database. A nonempty SHM is inspected and pinned, not ignored. The salt and last-frame checksum bytes participate in the header's self-checksum but cannot be compared with a WAL header when WAL length is zero; the receipt explicitly marks them unbound.
3. Open the source with SQLite URI `mode=ro` and `query_only=ON` (never `immutable=1`). Under one read transaction, run `integrity_check`, `foreign_key_check`, and a bounded per-table logical fingerprint. The output contains table counts and hashes, never business rows. The read may still update WAL shared-memory coordination bytes; this is disclosed and the post-sample must match exactly.
4. Make the backup within the newly created directory using exclusive file creation and Python's SQLite online `Connection.backup()` with bounded page steps, busy timeout, progress deadline, source-size budget, and row budget. Reopen it read-only for integrity and logical fingerprinting. Independently read the source again, then sample both source and backup physical signatures. A backup journal or unexpected backup sidecar is HOLD; a zero-length WAL and valid 32 KiB SHM are explicitly recorded.
5. Require exact source physical signatures before/after and equality of pre-source, backup, and post-source logical fingerprints. Record UTC start/end, SQLite version, source/backup identity and SHA-256, all physical samples, logic counts/hashes, and explicit policy HOLD. Write the JSON to a private pending file, flush and `fsync` it, then recheck deadline and source/backup signatures before atomically hard-linking the exact receipt name. A failed fsync or pre-publication deadline leaves no published receipt. The hard link is the final committing operation: if the OS delays it beyond the budget, this module cannot safely cancel it or claim a strict total-time bound. The receipt states `publication_operation_time_not_verified=true` and never grants execution authority; an independent formal runner would need its own elapsed-time evidence and fail-closed validity check.

The strict physical comparison intentionally rejects benign SHM coordination changes and detects writer/reader effects that appear in the sampled physical or logical signatures. It cannot prove the absence of a short-lived writer that restores the same observations. The WAL-index is transient shared-memory coordination data, not a recovery file; valid header checksums do not prove that no reader is attached, authenticate an empty WAL's salt, or validate unused hash slots/lock state. No retry loop silently waits for a passing moment. A busy or deadline error stays HOLD. The API does not infer Windows process identity or absence of open readers from loopback/SQLite headers. Format and checksum interpretation follow [SQLite's WAL-index format](https://sqlite.org/walformat.html#the_wal_index_header) and [SQLite's `walChecksumBytes`/`walIndexWriteHdr` source](https://www3.sqlite.org/matrix/ev/src/wal.html).

## Formal decision still required

Before this may be part of formal JIT, the owner must revise and independently review the f3 sidecar clause, approved source/volume/output/time/cost bounds, exact runner call and receipt schema, failure cleanup/retention, and per-phase recheck behavior. A fresh official source sample, active Task/PID/config identity, DB file and sidecar signatures, fixed volume identity/free space, no competing writer, and fresh author plus independent GO are still required. The formal source backup must not be run merely because this proposal or its tests pass. If live SHM changes or a reader/writer cannot be bounded, keep HOLD and use an approved maintenance window. Never delete/checkpoint a sidecar or overwrite a live DB to manufacture a pass.

Synthetic validation: `tests/test_catalog_online_snapshot_gate.py` creates only temporary SQLite databases and checks both a verified technical receipt and fail-closed cases. It does not access the formal catalog, Task, provider, or service.
