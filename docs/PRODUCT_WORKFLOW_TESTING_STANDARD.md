# 商品工作流状态机与回归测试标准

版本：`product-workflow-testing-standard/v1`
适用范围：商品事实、内容审核、发布计划、妙手 COMMON、渠道发布、回读与人工验收。

## 1. 核心原则

任何新 Bug 都不得默认按单个按钮、单个报错字符串或单个 Offer 打补丁。
修复必须依次回答：

1. 哪个业务状态没有被正式建模？
2. 哪一层才是该状态的权威来源？
3. 哪些同类状态可能出现同样的死路或误判？
4. 服务端合同如何让所有客户端得到同一个结论？
5. 哪个状态迁移测试可以阻止复发？
6. 真实浏览器与真实服务是否验证了同一份已部署资源？

## 2. 单一状态权威

- 服务端 `product-workflow-next-action/v1` 是用户下一步的唯一权威。
- 浏览器不得重新推导另一套业务状态机，只负责呈现、聚焦与发起已有受治理动作。
- 不可变 ReleasePlan、ReleaseRun、target receipt 和官方 readback 高于旧页面缓存与旧预发布观察。
- 只有与当前计划身份、digest 和回读证据完全一致的持久结果才能推进状态。
- 任何非终态必须投影一个可执行 control/link/refresh/manual handoff；禁止“所有控件禁用且无去路”。

## 3. 五层回归门

### L1 纯状态矩阵

覆盖每个标准状态：

- 商品事实不完整
- 内容未审核
- 商品未批准
- 发布计划输入待修复
- 发布计划待批准
- 妙手 COMMON 待准备
- PENDING 目标可发布
- RUNNING 目标只监控
- SUBMITTED_UNVERIFIED 待人工验收
- FAILED/RECONCILIATION_REQUIRED 待对账
- 能力缺失
- 全部完成

断言：每个状态只返回一个 next action；非终态均通过 `assert_no_dead_end`。

### L2 合同与错误形状

- malformed/null/错误类型必须 fail closed。
- 旧字段、缓存字段与新持久回执冲突时，按明确优先级选择权威事实。
- 所有 reason code 稳定、脱敏、可被 UI 和测试消费。

### L3 临时 SQLite + HTTP

- 用临时库执行真实状态迁移，不只 mock 最终 JSON。
- 验证 claim、attempt、receipt、external write evidence、replay 和 rollback。
- 每个修复必须覆盖成功、提交前失败、提交后歧义、重复请求。

### L4 Chromium 用户旅程

- 1440×900 与 390×844 两个视口。
- 每个非终态必须存在一个可见、可点击的主下一步入口。
- 点击入口必须到达实际可操作控件；不得只滚动到另一个禁用死路。
- 所有禁用控件必须有可见原因。
- 网络预算和写入次数必须被断言；只读旅程 POST=0。
- console/pageerror=0，无横向溢出。

### L5 真实服务验收

- 重启后核对 PID、端口、静态资源版本和 API schema。
- 使用当前正式页面读取真实 Offer 状态，但不自动触发外部发布。
- 验证服务端 next action、页面主入口和实际控件三者一致。
- 若真实结果与 fixture 不同，测试未完成，不得宣称修复。

## 4. Bug 修复完成定义

一项修复只有同时满足以下条件才能关闭：

- 根因归入状态机/合同/持久化/交互/部署中的明确类别。
- 同类状态已统一处理，不使用 Offer ID、文案字符串或页面位置特判。
- 纯状态矩阵新增或更新。
- 至少一项真实状态迁移测试覆盖。
- 至少一项浏览器旅程覆盖用户看到的入口和反馈。
- 受影响测试、相关测试和部署后真实页面验证均通过。
- 没有真实平台写入时，报告必须明确 `external_writes=0`。

## 5. 禁止项

- 仅修改按钮 `disabled` 条件而不修改服务端状态合同。
- 依赖错误文案包含某个字符串来决定业务状态。
- 用 mock 绿色替代 SQLite/HTTP/浏览器迁移测试。
- 测试旧静态资源但宣称当前服务已修复。
- 为绕开死路清库、改历史 proof、重置 attempts 或重发已有外部结果。
- 将“已提交”“草稿已保存”“官方回读成功”混为同一个成功状态。
