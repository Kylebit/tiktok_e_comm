一、先看结论

正确方向01–04 在发布中心你负责校对事实、内容、SKU 和发布选择，最终生成不可变的“已批准商品快照”。
需要收敛05–07 由 Skill 负责Skill 应分别执行 TikTok、Shopee、Ozon，回读平台事实，处理已确认故障并输出一份报告。
当前核心矛盾两套执行入口并存网页按钮目前直接调用服务端发布接口，并没有调用 Skill。Skill 另有自己的 CLI、报告和判断。
最重要的审计结论：现在不是“Skill 已完全接管 05–07”，而是“网页直发”和“Skill 编排”同时存在。两者使用不同状态、不同报告、不同回读深度，这正是界面与后台结果经常不一致的结构性原因。

二、商品上架七阶段

01

商品事实

读取来源商品，建立 SKU、规格、成本、重量、包装和来源身份。

02

内容审批

确认标题、描述、图片、视频和内容顺序。

03

商品审批

确认 Seller SKU、变体关系和每 SKU 商业资料。

04

发布计划

确认平台、店铺、价格、类目和本轮选择，并冻结快照。

05

准备发布

Skill 读取快照，为每个平台生成独立任务与确定性命令。

06

渠道执行

分别调用妙手、Shopee、Ozon；平台之间不互相阻塞。

07

回读对账

从权威来源回读，核对商品、SKU、价格、图片和状态。

六、三个平台的详细流程

TikTok · 妙手

  1. 按用户选择建立精确目标列表。
  2. 每个店铺独立取得并保存 detail_id。
  3. 写入逐 SKU 规格、价格、包裹、类目与图片。
  4. 回读草稿，逐 SKU 校验。
  5. 调用妙手正式发布任务。
  6. 保存妙手接受事实；有官方回读才判最终成功。

Shopee · 全球与区域

  1. 创建/更新 CNSC 全球商品。
  2. 官方回读 global_item_id、model、图片、描述。
  3. 按用户选择逐区域发布。
  4. 每个站点使用本地价格、物流与币种。
  5. 官方回读区域 item 与 global linkage。
  6. 各站点独立分类，不互相阻断。

Ozon · 官方 API

  1. 枚举所有批准 SKU。
  2. 为每个 SKU 生成独立 offer payload。
  3. 调用官方 import。
  4. 按 offer/id 轮询官方状态。
  5. 核对标题、价格、图片与所有 SKU。
  6. 部分接受不得报告整品成功。

九、测试与验收应该怎么做

L1

确定性红测/回归

请求字段、多 SKU、价格、类目、状态分类、错误边界。无外部写入，运行快。

L2

真实只读预检

真实凭据加载、类目树、店铺映射、旧商品状态和 API schema；不发布。

L3

授权 Offer 实写

用明确授权 Offer 点击真实按钮，写入平台，官方回读，并保存真实前端截图。

每个改动必须保留的最小测试路径

  1. 先用最小失败测试证明问题确实存在；记录修改前失败证据。
  2. 修复后运行该红测和平台相关回归，不必每次跑全仓所有无关测试。
  3. 凡是发布链路或页面按钮改变，必须运行一次真实浏览器点击测试。
  4. 凡是结果分类改变，必须使用授权 Offer 做平台回读，不以 mock 的 HTTP 200 代替。
  5. 输出：请求是否发出、外部写入次数、外部 ID、官方回读、截图、修改前后对比。

当前缺口：没有一个集成测试能完整证明“真实页面点击 → 与 Skill 相同的工作流 → 官方回读 → durable 报告 → 页面显示”在三个平台都成立。Shopee 区域多 SKU 流程也没有进入 Skill 脚本的固定回归矩阵。

十、审计发现：不合理、矛盾与改进点

P0
两套执行权威
网页按钮直接调用服务端发布接口；Skill 是独立 CLI。相同业务由两套编排、两套状态和两套回读执行。
改进：网页三个按钮调用 Skill 平台任务，或服务端复用同一个 Skill runtime；禁止复制一套近似逻辑。
P0
Shopee 区域能力未进入 Skill
Skill 只包含全球商品 dispatch/readback。3838608018 的四区域发布是 Agent 临时调用生产 helper 完成。
改进：新增 dispatch_shopee_regions.py 与 readback_shopee_regions.py；一个站点一个结果。
P0
区域状态可被错误预填
upsert_global_entry 使用 published_regions or [MY,TH,PH,VN]；传空列表也会被写成四站已发布，即使没有任何 shop_item。
改进：空列表必须保持空；只有官方取得区域 item_id 后，record_shop_item 才能添加地区。
P0
状态真相分裂
浏览器、release_v1、oneclick、Skill 报告和平台回读可能互相矛盾，因此出现“后台成功、界面失败”或反向误报。
改进：平台回读最高优先；Skill 生成 durable report_id；页面只投影报告，不自判成功。
P1
Shopee 全球价格身份不清
一个 CNSC global model 只有一个全球价格，但快照中存在多个目标价格来源。没有明确 master CNY price 和区域 local price 的边界。
改进：快照显式保存 shopee_global_price_cny；区域站点另存逐 SKU 本地币价格。
P1
TikTok 回读不足以证明店铺成功
当前主要证明妙手草稿、任务或账本状态；对于缺官方回读的站点，妙手接受仍可能被理解成发布成功。
改进：无官方店铺回读时统一为“平台处理中”；只有权威商品事实可读才升级成功。
P1
报告不一定持久化
Skill 未显式指定 --report 时可能只生成临时输出，产品中心无法关联这次执行。
改进：每次执行固定保存到 offer/revision/run 目录；数据库保存 report_id、路径和摘要。
P1
执行依赖与输入血缘混淆
定价阶段可参考 TikTok 历史，但批准后 Shopee/Ozon 不应运行时依赖 TikTok。旧 oneclick/COMMON 规则仍容易造成错误阻断。
改进：明确“共享只读输入允许、运行时依赖禁止”；批准快照必须自包含。
P1
05–07 产品定位矛盾
用户已决定 05–07 Skill 化，但产品中心仍保留自己的完整发布状态机和直发按钮逻辑。
改进：产品中心 05–07 改成“交接给 Skill / 查看 Skill 报告”，或真正内嵌同一个 Skill；只能选一种。
P2
全量扫描导致超时
正常发布期间扫描所有店铺/所有 SKU 会放大延迟和网络不确定性。
改进：常规路径使用批准时保存的 exact identity 直接读回；全量 reconciliation 另做异步工具。
P2
阻断与提醒过多
