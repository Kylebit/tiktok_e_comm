## 为什么重写这套规范

过去两周，需求、历史实现和安全治理规则在同一套状态与页面中持续叠加，导致以下概念被混在一起：

- 上一次发布结果与下一次显式发布资格；
- 妙手接受提交与目标店铺最终上架成功；
- 当前批次状态与历史审计记录；
- TikTok、Shopee、Ozon 三个平台的独立操作；
- 产品必要条件与工程团队自行增加的保守限制；
- 当前实现行为与 Kyle 实际确认过的需求。

本目录重新建立唯一、可追踪的产品依据。任何代码、测试或旧文档与本规范冲突时，不得自行选择其一；必须先提交规范差异，由 Kyle 确认后再改变产品行为。

## 评审顺序

1. [PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md)：用户要得到什么、什么明确不做、如何验收。
2. [ARCHITECTURE.md](ARCHITECTURE.md)：系统边界、平台隔离、数据所有权和状态模型。
3. [DETAILED_DESIGN.md](DETAILED_DESIGN.md)：按钮、接口、批次、目标状态、错误和并发的精确行为。
4. [VISUAL_TEST_PLAN.md](VISUAL_TEST_PLAN.md)：真实点击、每条状态路径、截图证据和浏览器门禁。
5. [TRACEABILITY.md](TRACEABILITY.md)：每条需求对应的实现位置、测试门禁和当前差距。

## 规范优先级

从高到低：

1. Kyle 对当前版本作出的明确书面确认；
2. 本目录中状态为 `APPROVED` 的需求；
3. 已通过的变更单；
4. 生产代码和自动化测试所反映的现状；
5. 旧文档、历史兼容逻辑和注释。

生产代码或测试不能反向创造产品需求。测试只能证明实现满足已批准需求，不能因为已有测试存在，就把测试中冻结的旧行为自动升级为新需求。

## 冻结规则

- 文档批准前，不根据本草案修改生产发布逻辑。
- 文档批准后，所有代码任务必须引用需求 ID。
- 未关联需求 ID 的产品行为变更不得进入实现。
- 新增阻断、依赖、审批、对账、自动重试或跨平台联动，必须先有 Kyle 批准的变更单。
- Bug 修复遵循 `docs/TESTING_GOVERNANCE.md`：稳定复现、修改前红测、解释根因、再修复和回归。

## 本次评审最重要的五条结论

1. 每次点击某个平台的发布按钮，都是该平台的一次全新显式尝试。
2. 上一次成功、失败或结果未知，只进入历史；不得决定下一次能不能开始。
3. 同一商品的 TikTok、Shopee 全球商品、Ozon 三个平台互不依赖、互不禁用。
4. 当前正在执行的同平台批次可以暂时阻止并发重复点击；其他历史状态不可以。
5. 页面必须把“当前操作”与“历史结果”分区，不能再用“上次结果未确认”占据主操作入口。

## Kyle 已确认的交互决定

1. 同平台 attempt 仍在执行时，重复点击只显示提示；不跳转、不聚焦、不创建第二个并发 attempt。
2. TikTok 草稿 proof 缺失时保留两步：先重新导入采集箱，再显式点击发布 TikTok。
3. 历史完整持久化用于审计，但主发布页面不主动提示历史，也不显示历史条数。
4. 最近一次 attempt 即使已终态仍属于“本轮”；下一次 attempt 创建后才转入历史。
5. 每个按钮与每个状态变体都必须有真实浏览器点击和截图路径证据。
