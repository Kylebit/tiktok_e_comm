# Manage Profit Settlement

Keep TikTok, Shopee, and Ozon execution independent. Never use one platform's settlement, advertising, SKU mapping, cursor, or result to complete another platform. Share only versioned cost and FX snapshots.

## Workflow

### Stage 1: official settlement evidence

1. Accept an explicit platform, site, inclusive start date, and inclusive end date. Confirm the period is closed in the site's reporting timezone.
2. Read [references/report-contract.md](references/report-contract.md) and the matching platform section in [references/platform-sources.md](references/platform-sources.md).
3. Pull and save settlement evidence before doing any profit calculation. Run `scripts/pull_settlement_evidence.py --platform PLATFORM --site SITE --start YYYY-MM-DD --end YYYY-MM-DD --project-root ROOT --output OUTPUT`. Pull only official settled/released finance records; reject pending, processing, cancelled, delivered-but-unsettled, or unknown states. Add `--allow-credential-refresh` only after explicit operator approval. For TikTok, refresh a disposable token copy and leave every production credential file unchanged. For Shopee, bind refresh to the token file under the explicit project root, retain a rotated refresh token by updating that configured file, and record the credential write scope in the evidence receipt.
4. Review the saved `settlement-evidence/v1` JSON and HTML with the user. Verify period/timezone, source counts, financial component names, detail failures, snapshot checksum, redaction, and `external_writes_performed=[]`. If the user requested only this first stage, stop here.
5. Keep API results in memory or an explicitly named redacted snapshot. Never run a legacy wrapper that cleans directories or overwrites CSV/HTML during a report preview.
5a. When the operator asks whether every order created in a period has settled, do not answer from a settlement-period report alone. Pull the complete official created-order set in the site's timezone, observe Finance settlement through an explicit as-of date, and run `scripts/audit_tiktok_settlement_coverage.py`. Report total cancelled orders, cancelled-with-settlement/refund, cancelled-without-settlement, and non-cancelled-without-settlement separately; never label only the last cancelled subset as the total. A cancelled order without Finance evidence is not a missing settlement, while a delivered or in-transit order without Finance evidence remains unsettled.

### Stage 2: order-level profit

6. Build a versioned cost snapshot keyed by canonical seller SKU and one immutable FX snapshot from a live read for the whole run. Stop if every live provider fails; never substitute configured/default rates. Retain the provider, provider as-of time, snapshot identity, and full-precision CNY-per-local rate. Apply temporary cost policy `temporary-cost-policy/default-5-conflict-high/v1`: use CNY 5 per unit when no positive cost exists and select the highest positive value when catalog costs conflict. Retain an assumption warning on every affected report/SKU; never present either selection as catalog fact.
7. Adapt only reviewed `settlement-evidence/v1` artifacts. Run `scripts/build_weekly_from_evidence.py --evidence-dir EVIDENCE --project-root ROOT --output OUTPUT --start YYYY-MM-DD --end YYYY-MM-DD`. For one independent site artifact, add `--platform PLATFORM --site SITE`; never combine different Shopee sites into one report. Use the bundled `report-policy.json` as the single editable location for all three weekly advertising fractions and the TikTok/Shopee local-fulfillment fees. It defaults every platform to `0.22` and charges CNY 4 once per local TikTok or Shopee parent order. Use `--policy-config PATH` for another versioned policy file, `--ad-rate RATE` or the three platform-specific ad-rate flags for one-run advertising overrides, and `--tiktok-local-fulfillment-fee-cny` or `--shopee-local-fulfillment-fee-cny` for one-run platform fee overrides. The script records the policy checksum and resolved values, reads `shop.db` with SQLite `mode=ro`, requires a live FX source, and writes report artifacts only.
8. For weekly reports, default each platform's advertising fraction to `0.22` (22%) unless the user supplies an explicit global or platform override. Apply the rate to the buyer's cash-paid **product** amount, never net settlement and never buyer shipping. For TikTok this is `customer_payment - customer_shipping_fee`; for Shopee it is `buyer_total_amount - buyer_paid_shipping_fee`. Retain the seller-discounted product sales amount separately for commercial analysis, but do not use platform-funded voucher value or shipping in the estimated advertising basis. Preserve the rate, input source (`default_22`, global override, or platform override), policy version, basis amount, and basis lineage in every report; never label the weekly estimate as actual spend. Exclude an actual TikTok advertising adjustment from the weekly order-settlement basis before applying the estimate, and reconcile the exclusion separately so advertising is never deducted twice.
9. For TikTok/Shopee monthly reports, require actual advertising evidence by default. Prefer order attribution; otherwise allocate an auditable actual total by buyer-paid GMV. For a TikTok order-created month, run `scripts/build_tiktok_monthly_from_evidence.py`; filter settled order rows by official `order_created_at`, while keeping their later settlement dates and facts. Use only `GMV Payment for TikTok Ads` Finance charges dated inside the requested calendar month as actual advertising evidence, retain the FX and statement lineage, and attach a non-order adjustment with `related_order_id` to its original order. An operator may explicitly request an estimated monthly override with `--ad-rate RATE`; then calculate every included order from its buyer cash-paid product amount, label the result `realized_settlement_with_estimated_ads`, retain actual Finance advertising as `reference_only_not_used_in_profit`, and fingerprint the rate/source. Never silently fall back to zero or the weekly rate, and never call an overridden estimate actual spend.
10. Default Ozon weekly and monthly V1 estimated advertising to `0.22`, but accept an explicit operator override and label it `operator-adjustable-ad-rate/v1`; never label it actual spend. Derive the advertising basis from positive `OperationAgentDeliveredToCustomer` product-sale components. When the finance artifact contains only platform SKU and no quantity, `--allow-ozon-read-enrichment` may read `/v3/product/info/list` and `/v3/posting/fbs/get` to obtain seller SKU and fulfilled quantity. Retain only redacted mappings/counts, never raw responses or credentials.
11. Generate one independent JSON/HTML report per platform and site. For TikTok and Shopee, query official order details by the settled order ID, retain explicit `create_time` as `order_created_at`/`occurred_at`, and display it independently from settlement time; never substitute payment, shipment, completion, release, or settlement time for missing order time. Do not invent an Ozon order-created time when the official read exposes only processing or shipment timestamps. Apply Shopee fulfillment evidence by site. For MY, classify the order cross-border when `sales_tax_on_lvg` (the 10% low-value-goods sales tax) is present and non-zero, and local when that field is present and zero. For VN, classify the order cross-border when `vat_on_imported_goods` is present and non-zero, and local when that field is present and zero. Classify every PH order as cross-border. For TH, classify the order cross-border only when both VAT on imported goods and import duty are non-zero; if both fields are present but either is zero, classify it local. Treat a required site-specific tax field as blocking when absent. Charge one combined local shipping-and-warehouse fee once per parent order, allocate it deterministically across its item lines, retain the allocation and policy, and include the policy in the run fingerprint. Consolidate multiple same-period settlement facts for one order line only when product identity and quantity agree and no more than one fact carries a positive advertising basis; otherwise fail closed. Sum settlement and fee facts, charge product cost and estimated advertising once, and retain every source fact identity/time in JSON and HTML. Keep the initial order-line projection sorted by settlement timestamp descending, with order ID and order-line ID as deterministic tie-breakers. Make the HTML order-created header toggle ascending and descending display order without mutating JSON; keep missing order-created times last in either direction and use the same identity tie-breakers. Add inclusive order-created start/end date filters to HTML. After every filter change, show the unique parent-order count, visible item-unit row count, and unique parent-order count for each visible date; never count expanded quantity rows as separate orders. While a date filter is active, recompute the sticky bottom totals from only the visible rows for settlement, product cost, advertising, local fulfillment, profit, buyer amounts, AMS, external costs, and every dynamic fee column. Label them `筛选合计`; clearing the filter restores the server-rendered whole-period totals. Filtering changes only the HTML projection and never mutates JSON or the audited period totals. Hide the Shopee order-line ID column in HTML while retaining it in JSON and as a deterministic sort/deduplication identity. Render visible settlement, order-created, and FX as-of times as `YYYY-MM-DD HH:MM:SS（UTC±HH:MM）`; retain the original timezone-aware values in JSON and the HTML sort metadata. Follow the legacy order-profit table pattern: show only Seller SKU; place net settlement CNY, total product cost CNY, advertising CNY, combined local-fulfillment CNY, profit, and margin immediately after it; place product name at the far right. Render fulfillment type, order/product/quantity, Shopee product sales and buyer cash-paid product amounts as separate columns, live FX rate/provider/as-of time, unit cost, advertising basis/rate/input-source/local amount, external cost, and every platform fee component as its own column. Replace the redundant currency column with a dedicated Chinese `联盟营销佣金(AMS)` column for `order_ams_commission_fee`, showing both local currency and CNY, and suppress that code from the later dynamic fee columns so it appears exactly once. Calculate Shopee affiliate-order share from settled parent orders, not item lines: a parent order is affiliate when its period report lines sum to a positive CNY `order_ams_commission_fee`; retain affiliate, non-affiliate and total parent counts, the exact share, CNY fee total and local-currency totals in JSON, and display the percentage with numerator/denominator in HTML. Display only the country/region code in the country column and render a valid HTTPS main-image URL as an image rather than escaped markup. Display the FX rate at eight decimal places so small ratios remain meaningful; show price and cost values at two decimal places while retaining full Decimal precision and FX snapshot identity in JSON. Give wide HTML tables synchronized horizontal scrollbars above and below the order rows so every column remains reachable without scrolling to the final row. Review totals, every quality issue and assumption warning, negative-profit lines, fee inclusion semantics, source counts, settlement reconciliation, cost conflicts, and rejected rows.
11a. Define report GMV as the sum of each line's buyer cash-paid product amount converted with that line's audited FX rate. Show it as `总成交额（用户实付）`. Define both the whole-report margin and every product-line margin as profit divided by this user-paid GMV, never by net settlement or seller-discounted product sales. When date filtering is active, recompute visible GMV, profit, and margin from the same visible rows. Label external cost as a non-platform cost not already included in net settlement, show its local-fulfillment component explicitly, and explain when it consists entirely of the configured per-parent-order local-fulfillment fee. Never double deduct platform commissions, taxes, or fees already included in net settlement.
12. Perform two audit passes from each JSON artifact. Recompute totals from order lines and confirm only settled rows were included. Treat absolute reconciliation differences up to `1e-12` local currency as Decimal allocation noise while retaining the exact difference and tolerance; larger differences remain blocking. Iterate with a failing fixture/test when an issue is reproducible.
13. Approve only a ready monthly report after explicit human confirmation. Use `scripts/profit_report.py approve-monthly`; never approve a weekly or needs-review report.

### TikTok Thailand fulfillment classification

For TikTok Thailand, classify local versus cross-border only from the settled Finance tax breakdown. Preserve `import_vat` and `customs_duty` as independent Decimal components. If either component is non-zero, classify the order `cross_border`; if both are present exact zeros, classify it `local`; if either field is absent or invalid, use `unknown`, emit `missing_fulfillment_tax_evidence`, and keep the report in `needs_review`. Charge the configured local-fulfillment fee once per local parent order, default CNY 4, and allocate it deterministically across item lines; never charge cross-border or unknown orders. Apply operator policy `zero-settlement-unshipped-ads-only/v1` when a TikTok parent order's summed local-currency net settlement is exactly zero: keep estimated/actual advertising cost, but recognize neither product cost nor local-fulfillment cost because the goods were not shipped. Preserve the catalog cost as unrecognized evidence, plus the decision and policy version, in JSON. Do not apply this rule to negative settlements without separate evidence. Retain the allocation, resolved policy, parent-order counts, and policy fingerprint in JSON. Do not retain, display, or use order API `fulfillment_type`, delivery, shipping, or warehouse fields: they describe the fulfillment operator and do not prove the customs route. Hide the order-line ID column in both TikTok and Shopee HTML while retaining it in JSON and HTML sort metadata.

## Safety gates

For an operator-confirmed customer-refusal return, recognize product-cost loss by the settled customs route: a local-fulfillment return is assumed resalable and recognizes zero product-cost loss; a cross-border return is assumed destroyed and retains the full product cost. In both cases retain actual Finance refund/shipping components and any incurred advertising or fulfillment costs. Never infer customer refusal from a negative settlement pattern alone; require official reason/status evidence or an explicit operator-confirmed exception fact, with provenance in the report fingerprint.

- Treat platform reads as external reads, never writes. Require `external_writes_performed=[]` from an injected live adapter receipt.
- Default to no credential refresh and save a blocked receipt when a read credential is missing or expired. After explicit operator approval, TikTok may refresh only a disposable copy for that read run; record `credential_refresh_performed=true` and never overwrite the configured or fallback token source.
- Do not persist previews, mutate production databases, silently refresh credentials, send notifications, retry payments, or modify platform orders.
- Preserve raw fee names and normalized codes. Subtract only costs not already included in net settlement.
- Represent missing money as a quality issue, never numeric zero. The only current exception is the explicit temporary missing-cost policy, which uses CNY 5 and must emit an assumption warning.
- Keep approved knowledge artifacts immutable. Create a new report version for corrections.
- Do not store tokens, cookies, authorization headers, API keys, or raw responses in reports or knowledge artifacts.

## Iteration rule

Treat this skill as a versioned operating procedure. After each real report, capture reproducible adapter, status, fee, allocation, or reconciliation failures as synthetic/redacted fixtures; add a failing test; update the domain engine and the relevant reference; validate the skill; then rerun focused and full tests. Never encode a one-off order ID or marketplace response as a permanent rule.
