# Explicit session recovery adapter

`scripts/session_recovery.py` prepares one frozen file/target plan, accepts a separately supplied authorization receipt through `execute`, and exposes only `--dry-run PUBLIC_PLAN.json` on its CLI. Dry-run reads that public plan and source hashes only: no credential read, ACL operation, write or network. `prepare` reads source hashes and file metadata, not credential contents. Neither function grants authorization. A receipt must bind `plan_digest`, `auth_write=true` and the actual authority reference supplied after approval; never manufacture a real approval from a synthetic test.

## Persistence and reconciliation

The adapter verifies an existing protected directory and file before reading credentials. Windows owner must be the current user; only simple allow ACEs to the user, SYSTEM or local Administrators are accepted. Unknown/null ACL, broad access, symlink/reparse paths fail closed; the adapter never changes ACLs. POSIX equivalent requires current ownership and no group/other mode bits. **This strict check may reject the real existing directories.** Actual ACLs were not inspected or altered in U04-G. A future authorization/preflight must resolve that blocker explicitly, not weaken verification.

An exclusive sibling `.recovery-lock` serializes cooperating adapters. Other token writers must be stopped before execution; this lock cannot constrain unrelated software ignoring it. Expected size/mtime/inode is checked, then original bytes are held in memory and compared again before replacement. Public plans do not contain secret-file hashes. These checks detect ordinary concurrent changes, not a malicious same-user writer restoring metadata or racing replacement.

Each file/target has a fixed `.recovery-state-<shop-id-or-tiktok>.json` journal. The adapter saves an ATTEMPTED record before calling transport. Journals are not reset by new run IDs; an existing run requires reconciliation. Per-target maximum is refresh + identity = two attempts; the five fixed targets total ten. Four Shopee targets share the credential-file lock, run serially, and each new plan must use the current file version after the previous update. Preparation of all four plans from the same old version intentionally causes later plans to fail rather than overwrite another update.

Under the already protected parent, backup/candidate/replacement names contain provider target and run ID. Before refresh, both candidate and replacement are exclusively created while empty, their protection and file identity checked, and flush/fsync attempted. Occupied paths, creation or protection failures stop with zero requests and never overwrite prior files. The adapter keeps both handles open through persistence. Windows denies other write/delete opens and atomically renames the reserved replacement by its retained handle, without reopening the source path; readback checks that same handle and destination file identity. POSIX keeps the descriptors and checks identity around rename, but the cooperative-writer limitation above still applies. New secret bytes go only through these verified reservations. The backup is byte-exact; replacement preserves all unselected Shopee entries and the sync map. A whitelisted refresh candidate is retained only in that private directory, including on local validation/persistence failure after possible rotation. Raw responses, provider error strings and secret hashes are not persisted. Response size is capped at 1 MiB; JSON duplicates/nonfinite values, blank tokens, invalid expiry and wrong IDs are rejected.

After a possible refresh attempt, any request/validation/save failure becomes RECONCILIATION_REQUIRED; the old file is unchanged if replacement did not occur. Pre-dispatch reservations do not guarantee later disk writes/fsync will succeed: post-response media or permission failure can still leave an empty/partial candidate and require operator/provider recovery. A later replacement failure preserves the completed candidate when its own write succeeded. No request is retried and no old token is rolled back as if valid. An already spent attempt or orphan lock is never replayed automatically. Failure after replacement or during identity leaves the new credential in place and reports unverified state; a local backup cannot undo provider rotation, so there is no automatic rollback. An ATTEMPTED journal remains fail-closed if later state persistence fails. Removal/reconciliation of locks, journals or candidates is not an automated capability of this package.

Refresh expiry is not silently normalized. Saved far-future timestamps (including the observed 2125 value) remain unchanged and report UNKNOWN_IMPLAUSIBLE_SAVED_EXPIRY; missing/non-integer refresh expiry reports UNKNOWN. These states do not claim provider validity. TikTok new access expiry is validated as an absolute timestamp, Shopee `expire_in` as duration per existing source contracts, pending live contract verification.

## Validation boundary

Windows rename metadata is constructed before dispatch using the actual UTF-16 code-unit count plus an in-buffer NUL, rather than Python character count. Unsupported destination encoding fails before refresh. Synthetic non-BMP paths are tested across four trailing lengths to exercise alignment boundaries; these follow-up results are separate from the earlier 153-node run.

Tests use visibly synthetic credential fixtures under the independent U04-G audit root. Only those new fixture ACLs are restricted with icacls; real files/ACLs are never inspected. Calls exercise the actual R transport with its lowest request/opener boundary controlled, verifying one physical attempt, no curl, rejected redirect and certificate failure. This is controlled transport evidence, not a live TLS handshake or provider acceptance. No external socket, auth API or order API is called. Prior U04-F findings about unsafe TLS/retry belong to **D**, not R; prior sealed artifacts remain intact and this document supplies the correction.
