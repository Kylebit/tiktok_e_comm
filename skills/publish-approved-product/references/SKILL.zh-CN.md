# 已批准商品发布 Skill（中文镜像）

## HomeBloom SEA 四站（妙手）

- `tiktok:HB_PH`、`tiktok:HB_MY`、`tiktok:HB_TH`、`tiktok:HB_VN` 都是
  TikTok 的独立发布目标，必须走妙手开放 API，不得改走 TikTok 官方 API。
- 四站必须分别绑定 HomeBloom 的精确店铺：PH `15173238`、MY `16770639`、
  TH `16770557`、VN `16783702`。
- 同一国家的 LivelyHive 店铺不能替代 HomeBloom；每站的妙手 `detail_id`、
  写入回执、回读和最终状态都必须独立保存和验收。

## Shopee 区域语言（已确认规则）

- CNSC 全球商品保留批准后的英文标题和英文描述。
- 从全球商品发布到 PH/MY/TH/VN 时，区域创建请求不得主动发送
  `item_name` 和 `description`；否则会用英文覆盖 Shopee 的站点翻译。
- PH、MY 回读为英文可以接受；TH 必须回读为泰语，VN 必须回读为越南语。
- 如果 TH/VN 仍是英文，只修改同一个已经创建的 `item_id`，然后再次通过
  Shopee 官方 API 回读；不得为了修复语言再创建一个重复商品。
- 修改响应丢失时不得盲目重试，以同一 `item_id` 的官方回读结果为准。

## 回读之后必须永久修复

回读不是每次发布后的人工补丁，它只负责证明平台事实。只要确认过一次
“批准快照与平台结果不一致”，就必须把根因固化到三处：生产代码的不变量、
修改前会失败的回归测试、对应平台的事故规则。以后相同错误应在发布前或
复用旧商品时被自动纠正，不能再次依靠人工发现。只有平台接受并且可回读的
标题、描述、SKU、规格、价格、图片、包裹和状态与批准快照一致，才允许显示
发布成功；本地提交记录只能证明请求已发送，不能证明商品正确。

这份文件供人工审核。TikTok、Shopee、Ozon 只共享最开始的“已批准商品快照”，之后完全独立。

## 核心流程

1. 要求准确的 `offer_id` 和已批准 `plan_id`，不得从可变工作台重新推导。
2. 只使用 `skills/publish-approved-product/scripts/product_center_publication.py` 启动生产发布。
3. 商品中心按 `offer_id + plan_id` 读取冻结 v4 快照，并对每个已授权平台独立执行“发布 → 官方或妙手回读 → 结果分类”。
4. 一个平台或店铺失败，不得阻止其他平台或店铺。
5. 对用户只显示：发布成功、平台处理中、部分成功、发布失败；详细证据保留在脱敏报告中。

## 唯一生产命令

```powershell
.venv\Scripts\python.exe skills\publish-approved-product\scripts\product_center_publication.py --offer-id <OFFER_ID> --plan-id <EXACT_PLAN_ID> --platform all --execute
```

该薄控制器只向三个商品中心入口发送 `{offer_id, plan_id}`：

- `/api/product-workspace/publish-tiktok`
- `/api/product-workspace/publish-shopee-global`
- `/api/product-workspace/publish-ozon`

它必须验证 HTTP 202、`product-publication-start/v1`、平台、`run_id` 和
`publication-report:<run_id>` 完全一致，然后轮询准确的 `publication-report`。
一个平台失败后仍继续启动其他平台。POST 结果丢失时不得自动重发。

`publish_approved_product.py`、`inspect_snapshot.py`、`dispatch_*.py` 和
`readback_*.py` 是已弃用兼容/诊断工具，不得作为新商品的生产发布入口。
生产命令不读取 dashboard、不重建商品事实、不调用旧 `/publish` 或旧采集箱启动接口。

## v4 冻结快照的唯一执行边界

`approved-publication-snapshot/v4` 是新发布任务唯一允许使用的商品输入，只能交给
v4 平台执行器。不得把它传给旧 ReleasePlan 解析器或旧采集箱启动接口。旧结构读取
的是另一套字段；已经确认它会先在妙手创建/认领平台对象，随后才因为字段结构不符
而中断，造成“有外部写入、没有店铺草稿身份”的不完整状态。

妙手 claim 请求中的本地幂等键不等于平台幂等。每次平台返回平台明细 ID 后，必须
先持久化该 ID，再继续类目准备、店铺草稿创建等可能失败的步骤。如果返回结果丢失
或不明确，必须先读取妙手官方列表并对账，绝不能因为本地幂等键相同就再次 claim。

`platform_scope` 是结构边界：只选择 TikTok 就只能创建 TikTok 行；只选择 Shopee
就只能创建 Shopee 行。不得为未选择平台建立 PENDING 行或完成依赖。

## 确定性脚本与 Agent 的分工

商品中心服务端的冻结 v4 执行器负责组织平台请求、调用 API、隐藏凭据、轮询和读取事实。

Skill 的薄控制器只负责准确启动身份、三个平台独立顺序、公开报告轮询和四态脱敏摘要；不得组织平台 payload。

商品中心在创建 run 时冻结 canonical Skill manifest digest、准确 Git commit，
以及当前平台生产执行文件实际内容的 code digest。后台 worker 必须在 RUNNING 和
任何平台调用前复算；漂移时以零 dispatch 持久化 FAILED，且不得隐式安装 Skill。

内部不可变报告只能保存固定八字段的目标脱敏证据：目标标签、状态、阶段、安全
provider code、已脱敏 reason、是否发起请求、结果是否未知、已确认外部写次数。
公开 API 与客户端仍只暴露四态计数，必须移除目标证据和执行身份；禁止 raw
response、headers、URL、token、异常参数和外部商品 identity。

Skill/Agent 负责执行顺序、类目策略、是否采用已确认的恢复规则、结果分类、向用户解释，以及把已验证事故沉淀到平台知识文件。

正式提交任何 TikTok 店铺前，先读取当前采集批次状态。如果可发布店铺集合少于本次批准的店铺集合，必须先建立一轮新的 TikTok 独立批次，全部准备完成后再提交；不能先发布旧批次中的少数店铺，再发现其余店铺没有可用草稿。

## TikTok 类目决策

妙手草稿里已有的类目只是未可信候选，不是最终决定。

1. 从批准快照读取产品类型、用途、材质、标题、描述和图片。
2. 对每个站点读取 TikTok 官方类目树。
3. 优先选择语义最准确且当前启用的类目。
4. 对桌垫/餐垫/杯垫及桌布/桌旗，Kyle 已确认统一直接使用 `600009`“节庆装饰”。
5. 不再先选 `600033` 或 `600204`；但 `600009` 仍必须在该站点官方类目树显示启用，且该店铺元数据有效。
6. 如果 `600009` 不可用，返回 `CATEGORY_CONFIRMATION_REQUIRED`，不得继续猜测其他宽泛类目。
8. 写入类目后必须读取同一草稿确认，再执行发布。

### 已确认：冰箱贴六站点官方类目

冰箱贴的准确官方类目是 `cid=854536`（`冰箱贴`）。本次已对
`PH/MY/TH/VN/MX/GB` 六个站点分别完成官方类目树与准确店铺元数据验证。但这不
代表以后可以无条件硬编码：每次发布仍要在各站点当前类目树中递归找到准确节点，
确认启用且语义为冰箱贴，再验证当前准确店铺的元数据。一个站点成功不能替另一个
站点背书，旧草稿或缓存也不能替代本轮验证。保存后继续按准确 `detail_id` 回读类目、
SKU、逐 SKU 价格、图片、重量和包装。

妙手返回的 `cateTree` 是多层树，不是平铺表。必须沿每个节点的 `children` 递归查找准确 `cid`；不能直接执行 `cateTree[600009]`。本次六店铺误报“类目不可用”的已确认根因，就是把嵌套树当作平铺表读取。

发布快照不能把已由站点官方树决定的类目重新覆盖成主类目。桌布/桌旗在快照中保留“各站点决定”，最终发布沿用草稿中已验证的 `600009`。任何 TikTok 站点或店铺草稿保存后，妙手都可能异步本地化或规范化标题；只要店铺身份、完整 SKU、价格、类目、图片、重量和包装仍准确，标题变化只记录为平台行为，不阻断发布。

这是一条明确的降级规则：不是因为标题出现节日词就选择节庆装饰，而是因为准确类目被 TikTok 限制，并且用户已经批准了该产品族的备用类目。

## TikTok 包装尺寸回读

- 批准快照和写入请求始终保留每个 SKU 的包装尺寸。
- 父级包装尺寸必须精确回读一致。
- SKU 行三个尺寸字段都返回时必须精确一致。
- SKU 行三个尺寸字段都不返回时，记录为妙手字段省略，不阻止该店铺。
- 只返回部分尺寸字段属于异常，阻止该店铺，但不影响其他店铺。

## TikTok 妙手异步回读

- 写入前的只读准备如果遇到瞬时失败，使用两轮、每轮最多三次的有界只读尝试，不得提前写入。
- 妙手接受草稿保存后，同一个 `detail_id` 的第一次回读可能仍是旧数据。
- 对同一草稿最多进行三次有界只读轮询；在轮询结束前，不把旧数据判成写入失败。
- 不得因为第一次回读陈旧而重复保存草稿。
- 第一个等待窗口结束后仍未生成的店铺，应先让其他独立店铺完成认领，再使用原 `detail_id` 复查一次；不得重复创建或认领。
- 单个店铺回读超时不得中断其他店铺。
- Skill 调用子脚本时固定使用 UTF-8 解码；Windows 默认 GBK 不得吞掉真实平台错误。

## 错误经验沉淀

只有经过“稳定复现 → 代码/API 证据 → 根因确认 → 红测 → 修复与回归”的经验，才写入平台知识文件。偶发网络错误和未经证实的猜测不得污染 Skill。

### 已固化：v4 快照误入旧采集箱解析

新 v4 快照与旧 ReleasePlan 的 `source_product/sku_prices` 结构不兼容。禁止为了
复用旧代码而调用旧解析器或旧采集箱启动接口；必须由 v4 投影与执行器直接消费冻结
事实。该错误已造成妙手平台 claim 成功、但六个店铺草稿身份都没有保存。

### 已固化：本地幂等键不能阻止妙手重复 claim

相同本地幂等键再次发送时，妙手仍可能创建新的平台明细。本地幂等不等于平台幂等。
必须在任何后续步骤前保存平台返回的平台明细 ID；身份丢失或结果不明确时，先用官方
列表对账，再决定是否允许新写入，绝不能直接重放 claim。

### 已固化：平台范围不能制造未选择平台依赖

TikTok-only 动作曾因为系统同时插入未选择的 Shopee PENDING 行而永远无法结束。
以后 `platform_scope` 只创建所选平台行。已经尝试或已有终态证据的行不可删除；只可
清理未选择且仍为零尝试、零写入的原始 PENDING 行。

### 已固化：规格结构分号导致同一变体被误判

批准规格键可能保存为 `;田园鲜花铺;;`，妙手不透明 SKU 键通过
`skuPropertyList` 解码后则是 `田园鲜花铺`。比较完整规格签名时，只删除妙手的
结构分号；批准键和平台原始键仍分别原样保留。不得删除选项名称内部的普通标点，
也不得按顺序、标题或模糊相似度匹配。

### 已固化：TikTok 草稿必须绑定准确店铺仓库

每个 SKU 保存前先完成准确规格绑定，保留该行妙手现有的正库存；冻结商品快照不能
编造库存。已有且唯一的本店仓库绑定可直接复用；否则读取该店铺官方仓库列表，按
已验证的启用/默认规则确定唯一仓库，再写入
`shopIdToWarehouseIdAndStockMap`。不得复用其他店铺仓库。库存缺失、无启用仓库或
观察到多个仓库都属于写入前失败，不得猜测。

## canonical Skill 与安装副本同步

仓库中的 `skills/publish-approved-product` 是唯一事实源。使用前先执行：

```powershell
.venv\Scripts\python.exe scripts\sync_product_publication_skills.py --check
```

只有人工审核同意安装后，才显式执行并再次检查：

```powershell
.venv\Scripts\python.exe scripts\sync_product_publication_skills.py --install
.venv\Scripts\python.exe scripts\sync_product_publication_skills.py --check
```

不得隐式安装：发布、测试或 Skill 校验都不能自动修改已安装副本。parity 不一致属于
部署问题，不能混用不同 digest 的说明与脚本继续发布。

### 已固化：TikTok 提交后的妙手字段规范化

妙手正式接受保存和提交后，读取接口会把 `deliveryOptionSetType=default`
显示为空、把空尺码图类型显示为 `image`，并可能省略每个 SKU 的三维尺寸。
提交前仍严格修复这些字段；提交后使用单独的回读比较器，只容忍上述已证实的
规范化，同时继续精确核对类目、父级包装、每个 SKU、每个价格和每个重量。
不能再把六店铺全部误报失败，也不能把部分缺失或真实不同当成规范化。

### 已固化：Ozon 桌旗误落入墙贴类目

批准标题中的 `table runner`、`table runners`、`table flag` 都是桌用纺织品的
确定证据，必须在历史 TikTok 类目映射之前命中 Ozon 桌布/桌旗配置。官方回读
如果返回 `DECLINED` 或 `DESCRIPTION_DECLINE`，界面必须显示为失败并保留安全
错误代码，不能显示“处理中”。旧商品为错误墙贴类目时，先按官方生命周期规则
清理错误商品，再以正确类型重新提交三个 SKU，最后逐 SKU 核对标题、价格、图片
和已创建状态。

### 已固化：Ozon 类目正确但仍沿用墙贴文案与包装尺寸

即使已经识别为桌布/桌旗类目，也不能继续调用旧的墙贴标题和描述生成器。
商品展示尺寸必须来自每个已批准 SKU 的规格名称，例如 35×140、35×200、
35×300；20×20×3 这类包装尺寸只用于物流字段，不能写进商品标题。桌布/桌旗
标题或描述中如果仍出现“自粘”“墙面”“贴纸”“PVC 薄膜”等墙贴语义，必须
在发送前拒绝。该规则需要覆盖本次所有 SKU，而不是只验证第一个 SKU。

### 已固化：Ozon 删除旧错误卡片前必须先归档

Ozon 对尚未创建、但已经审核拒绝的旧商品，直接调用删除接口会返回
`ITEM_IS_NOT_ARCHIVED`。需要先使用官方回读得到的 `item.id` 调用归档接口，
确认同一商品已经归档，再按 Seller SKU 调用删除接口。归档失败或回读仍未归档时，
本轮 Ozon 必须停止，不能发送替代商品，也不能盲目重复删除。

### Ozon 可执行异步回读

发布接口接受后，Ozon 常先返回 `OFFER_VALIDATED` 或 `IMPORTED`。Skill 会执行有界
只读轮询，直到全部 SKU 验证成功或出现终态错误；轮询绝不重复发布。用户不需要
为了获得最终状态再次点击发布。

### 已固化：Ozon 单位、俄语文案与三接口回读

Ozon `/v3/product/import` 的重量和尺寸是整数单位：每个 SKU 的公斤数乘
`1000` 转为克，厘米数乘 `10` 转为毫米；不能把 `0.1` 公斤直接写进整数重量，
也不能四舍五入或复用其他 SKU 的包裹数据。

冰箱贴准确类目 `17028743`、类型 `93785` 要求俄语标题与描述。Skill 从冻结商品
语义生成并保存绑定快照摘要的俄语文案回执，不能加入商品代码、商品 ID、品牌宣称或
其他新事实。Ozon 会把标题中的 `×` 静默删除，因此发送前必须拒绝这个字符，使用
`7 на 7 см` 这样的稳定俄语写法。

官方回读必须合并 `images` 和 `color_image`；主图进入 `color_image`、其余 6 张在
`images` 时仍是完整 7 张图。重量、尺寸、类型和属性读取
`/v4/product/info/attributes`，准确描述读取 `/v1/product/info/description`，并与
`/v3/product/info/list` 的同一个 `offer_id`、`item.id` 绑定。只读一个列表接口不算
验证完成。

Ozon 接受更新后可能短暂显示旧标题或旧内容。此时显示“平台处理中”，继续有界只读
回读；只有官方失败状态才显示“发布失败”，不得因为第一次回读旧数据就重复提交。
