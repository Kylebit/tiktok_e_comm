# Task Workbench observation

Read `docs/TASK_WORKBENCH_RULES.md` in the adopted repository. The user's current explicit scope overrides examples. This skill concerns observation and task presentation; it grants no execution, publishing, paid, credential, restart, deployment, or existing-session messaging authority.

1. Resolve each accepted work item from its coordinator/producer receipt. Retain original session, Operations task (if one already exists), attempt and target identities; never create an Operations task merely to make work visible.
2. Supply target, actual last evidenced stage, dated observation, blocker, ownership/handover scope and result route. An absent heartbeat means live status unknown. A file, task icon, HTTP 200, successful refresh or old status does not establish RUNNING.
3. For every product-related description, list, detail and review, bind a recognizable verified name and genuine main image/thumbnail to the exact product identity and targets. Retain IDs in details. Refuse conflicting image identity; show missing rather than borrow another or retired product. Verify refresh/back navigation and product changes do not retain a previous thumbnail.
4. Cover every registered accepted kind, including replenishment, engineering and cleanup; templates only constrain their existing execution contracts. Mark unconfirmed creator/video observation handoff as unconfirmed, preserving independent systems. Report registry coverage gaps; never infer a complete inventory from an empty or failed read.
5. Agent owns daily observation, diagnosis, already-authorized safe recovery and verification. Escalate only genuine business decisions/final review, personal login, new cost or authority changes, with reason, evidence and the smallest necessary action. Ordinary technical errors and estimable parameters remain Agent work.
6. Preserve original UNKNOWN and cumulative budgets. Reconcile original attempts read-only; do not resend business instructions, replay submissions or invent a recovery interface.
7. Update only the authorized coordinator observation manifest or isolated candidate. Do not race a domain writer. New manifest revisions carry source hashes and observation times; reading the summary must not renew them or maintain leases.
8. Before adoption, render the exact candidate resources in a real browser: desktop/narrow screen, refresh/back, expanded/collapsed evidence, empty/failed read, all registered kinds, product identity conflict, missing image and product switch. Distinguish isolated tests, source changes, independent acceptance, production adoption and actual business results.

For the integrated contract, bind the independently reviewed `scope_ref` and exact
product `lineage` receipts described in `docs/TASK_WORKBENCH_RULES.md`. Use the
repository's `scripts/update_work_observations.py` with a dated update receipt and
the current manifest SHA. Validate first; apply only to the already-authorized
coordinator manifest. It cannot change ownership/execution mapping or install a
monitor. Refuse concurrent writer locks and stale revisions. Never silently rewrite
a source fingerprint or freshen an observation just because a page was refreshed.
